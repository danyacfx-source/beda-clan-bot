# Перенос бота на новый VPS (общий PostgreSQL, без systemd)

Ситуация: на новом VPS есть один контейнер, куда вы заходите по SSH. В нём уже
работают PostgreSQL и два других бота. Systemd и Docker внутри контейнера нет,
поэтому бот запускается вручную из консоли (`scripts/run.sh`). Бот получает
**свою** роль и **свою** базу в общем PostgreSQL: у других ботов тоже есть таблицы
`guild_settings`, `tickets`, `warns`, и общая база привела бы к конфликтам.

Дамп данных — файл `beda_dump.sql` (plain SQL, PostgreSQL 15). Его нужно загрузить
в пустую базу **до первого запуска** бота.

## 0. Код

```bash
git clone <URL репозитория> beda-clan-bot
cd beda-clan-bot
git checkout main        # после слияния ветки с миграционными скриптами
```

Нужны `python3` с модулем `venv` (`apt install python3-venv`) и клиент `psql`
(`apt install postgresql-client`). Положите `beda_dump.sql` в корень проекта
(`/*.sql` в `.gitignore`, дамп не попадёт в git).

## 1. Своя роль и база

Скрипт идемпотентен: повторный запуск ничего не ломает. Подключение —
суперпользователем PostgreSQL (`PGSUPERUSER`, по умолчанию `postgres`), хост и
порт — через `PGHOST` / `PGPORT` (по умолчанию локальный сокет).

```bash
# при необходимости: export PGHOST=127.0.0.1 PGPORT=5432 PGSUPERUSER=postgres PGPASSWORD=...
scripts/pg_create_db.sh --db beda --user beda
```

Пароль роли спросят интерактивно или возьмут из `BEDA_DB_PASSWORD`. Скрипт:
создаёт роль `beda` (если нет), базу `beda` с владельцем `beda` (если нет) и
отзывает `CONNECT` у `PUBLIC` — это закрывает только базу `beda`: другие роли
(другие боты) не смогут подключиться именно к ней, суперпользователь по-прежнему
может. На их базы это не влияет, а доступ роли `beda` к чужим базам определяется
их собственными настройками (если у них `CONNECT` открыт для `PUBLIC`, `beda` туда
подключиться сможет, хотя и не будет иметь прав на их таблицы).
В конце он печатает строку `DATABASE_URL=postgresql://beda:***@host:port/beda` —
пароль в ней замаскирован, подставьте настоящий (спецсимволы кодируйте как `%XX`,
например `@` → `%40`). Пароль скрипт никогда не печатает.

Сменить пароль существующей роли: `scripts/pg_create_db.sh --reset-password`.

## 2. `.env`

Если старый хостинг доступен — скопируйте оттуда `.env` целиком и поменяйте
только `DATABASE_URL`. Иначе: `cp .env.example .env` и заполните.

Важные переменные:

| Переменная | Зачем |
| --- | --- |
| `DATABASE_URL` | `postgresql://beda:ПАРОЛЬ@127.0.0.1:5432/beda` — имеет приоритет над `DB_PATH` |
| `BOT_TOKEN` | токен бота (обязателен, `preflight --strict` проверяет) |
| `OWNER_ID` | ваш Discord ID |
| `GUILD_ID` | сервер для прав категорий и `/apply_permissions` |
| `BOT_LOG_CHANNEL_ID`, `MEMBER_LOG_CHANNEL_ID`, `MESSAGE_LOG_CHANNEL_ID`, `VOICE_LOG_CHANNEL_ID`, `MOD_LOG_CHANNEL_ID` | каналы логов |
| `TICKET_SUPPORT_ROLE_IDS`, `TICKET_CATEGORY_ID` | роли и категория тикетов |
| `RULES_MESSAGE_ID`, `RULES_ROLE_ID` | правила-гейт |
| `TEMP_VOICE_TRIGGER_IDS`, `TEMP_VOICE_CATEGORY_ID` | временные голосовые |
| `WHERE_PLAY_CALLER_ROLE_IDS`, `WHERE_PLAY_COMMAND_ROLE_IDS` | роли «Где играем» |
| `PANEL_PORT`, `PANEL_*_PASSWORD(_HASH)`, `PANEL_PUBLIC_URL`, `PANEL_OAUTH_*` | веб-панель, если используется |

`DB_PATH` и `DB_BACKUP_*` при PostgreSQL не нужны для данных (SQLite не
используется); автоматические бэкапы делаются через `pg_dump`.

Права: `chmod 600 .env`.

## 3. Загрузка дампа

```bash
scripts/pg_import_dump.sh beda_dump.sql
```

Скрипт читает **только** строку `DATABASE_URL` из файла `.env` проекта (или из
файла, указанного `--env путь`); сам файл не выполняется. Переменная окружения
`DATABASE_URL` используется лишь если в файле такой строки нет: в общем контейнере
она может принадлежать другому боту, поэтому файл всегда главнее (при расхождении
скрипт печатает предупреждение с замаскированным значением).

Скрипт отказывается работать, если в схеме `public` уже есть таблицы. Если бот
случайно успел стартовать, используйте `--force`: скрипт покажет целевую БД
(пароль замаскирован), имя базы и число таблиц и потребует **вручную ввести имя
базы**; только после этого схема `public` пересоздаётся (все её данные удаляются).
`--yes` пропускает вопрос, но только вместе с `--force` и только без терминала
(например, из cron/CI).

Загрузка дампа и выравнивание последовательностей (`setval` по `max(id)`, чтобы
новые тикеты/отпуска/ивенты не получили занятые номера) выполняются в **одной
транзакции** (`ON_ERROR_STOP`): при любой ошибке база остаётся как была. В конце
скрипт печатает число строк в `tickets`, `vacations`, `events`, `dossiers`,
`guild_settings`.

Бот при старте выполняет `CREATE TABLE IF NOT EXISTS`, добавляет недостающие
колонки (`ADD COLUMN IF NOT EXISTS`) и отмечает миграции в `schema_migrations`
через `ON CONFLICT DO NOTHING` — таблицы и записи из дампа уважаются.

## 4. Остановите бота на старом хостинге

**До** запуска на новом. Один токен — один процесс: иначе оба экземпляра будут
отвечать на каждую команду, и пользователи увидят дубли. Остановите старый
экземпляр (`systemctl stop beda-clan-bot` / `docker compose stop bot` /
панель хостинга) и убедитесь, что бот в Discord стал оффлайн.

Если дамп снимали с работающей базы, а бот на старом хосте ещё писал данные —
остановите бота и снимите дамп заново: всё, что появилось после дампа, потеряется.

## 5. Запуск

```bash
scripts/run.sh --background      # создаст .venv, поставит зависимости, preflight --strict, запустит
tail -f logs/bot.log             # логи
scripts/stop.sh                  # остановка (SIGTERM, до 30 с, затем SIGKILL)
```

`run.sh` без аргументов запускает бота на переднем плане (Ctrl+C — остановка).
Параллельные запуски защищены замком (`data/bot.lock`), так что гонка двойного старта
невозможна. Скрипт перезапускает бота через 5 с после падения; штатный выход (код 0) и
SIGINT/SIGTERM останавливают цикл. PID хранится в `data/bot.pid`: второй запуск
при живом процессе отклоняется. Preflight проверяет подключение к PostgreSQL,
печатает версию сервера и число таблиц в `public`, а при подключении к базе
`postgres` предупреждает, что это общая БД.

После перезахода по SSH бот продолжает работать (запущен через `nohup setsid`).
После перезагрузки контейнера его нужно запустить заново — автозапуска нет.

## 6. Проверка

В Discord:

- `/status` и `/health` — бот онлайн, БД в состоянии `ok`;
- тикеты: открытые и закрытые тикеты из дампа на месте, новый тикет получает
  следующий номер, а не дубликат;
- отпуска: `/setup_vacations`-панель работает, активные отпуска видны;
- ивенты (`/event_list`), личные дела, настройки сервера на месте.

В консоли:

```bash
psql "postgresql://beda:ПАРОЛЬ@127.0.0.1:5432/beda" -c "SELECT count(*) FROM tickets;"
```

## 7. После переезда

Набор ролей изменился (Поддержка / Водитель), поэтому:

1. Выполните `/setup_dossiers` заново — панель анкеты и настройки ролей обновятся.
2. Новые команды личных дел: `/dossier_panel`, `/dossier_add`, `/dossier_card`,
   `/dossier_reset`.
3. Проверьте `TICKET_SUPPORT_ROLE_IDS` и `WHERE_PLAY_*_ROLE_IDS` в `.env` на
   актуальные ID ролей и перезапустите бота (`scripts/stop.sh`, затем
   `scripts/run.sh --background`).

## 8. Откат

Пока старый хостинг не удалён, откат прост:

1. `scripts/stop.sh` на новом VPS.
2. Запустите бота на старом хостинге (его база не менялась). Данные, появившиеся
   на новом VPS, на старый не вернутся — если они нужны, снимите дамп:
   `pg_dump --no-owner "$DATABASE_URL" > rollback.sql`.
3. Повторный импорт на новом VPS: `scripts/pg_import_dump.sh --force beda_dump.sql`
   (потребуется ввести имя базы; схема `public` пересоздаётся, **все данные в ней удаляются**).

Держите `beda_dump.sql` и старую БД как минимум несколько дней после переезда.
Регулярные копии: `pg_dump --format=custom --no-owner "$DATABASE_URL" > beda.dump`.
